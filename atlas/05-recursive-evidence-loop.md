# REL: does earlier work change the next decision?

**REL is an external working procedure:** research the relevant uncertainty, act, check the result, preserve useful evidence and revise the next action. A host provides tools, storage, permissions and recovery.

The current [skill snapshot](../package/rel-current/SKILL.md) is supplied as readable material. It does not install itself, change model weights or enforce a security boundary merely because an instruction says so.

## The distinction that matters

We separately record whether a lesson was requested, read, retrieved, interpreted, applied and followed by a checked result. These are different achievements. A saved lesson is an artifact; improvement is an effect on later work.

The strongest comparison gives ordinary engineering the same facts, tools and work allowance. Otherwise, an apparent skill benefit may simply be the benefit of possessing information the control was denied.

## One useful result, with the right comparator

In the paper's reporting-service study, retained route observations reduced repeated database work by roughly **77%**. An ordinary factual handoff obtained the same kind of benefit. With matched factual history, REL used **55.4% more later-task tokens** than ordinary work. All policies completed their six later tasks correctly. [Study S4, paper section 6](../package/PAPER.md#6-observation-memory-less-rediscovery-not-necessarily-lower-total-cost).

The memory was useful. The additional procedure was not shown to be necessary for that benefit. Database work was an instrumented work proxy, not a measured 77% reduction in total time, electricity or inference cost.

## What REL is useful for now

- Keeping assumptions, failed attempts and rejected branches visible.
- Connecting a correction to the changed output rather than only to a rewritten note.
- Separating implementation success from a comparative improvement claim.
- Choosing proportionate verification and retaining reusable methods where they work.
- Returning to the programme's wider objective when locally reasonable steps cease to answer it.

These are supported uses and engineering practices, not evidence that every user, model or harness improves by loading the skill. Longer-term benefit, correct lesson interpretation and broad portability remain empirical questions.

An empty learning update can be correct: if a run adds no reusable lesson, do not manufacture one. If ordinary work matches or beats the extra process, retain the simpler method.
