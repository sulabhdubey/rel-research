# Does a learned procedure revision improve later method acquisition?

Run92 · 28 October 2026 · A6 procedure evolution and reversible reuse

**The tested revision changed some acquisition behavior but did not improve the saved method or later decisions.** One actual model authored a procedure revision from Run91 evidence. Eight fresh-session learners then compared the frozen and evolved procedures with the same information, tools and budgets. Every learner selected the same ordinary C method. Their later operation counts and outputs were identical, while the evolved condition used **20.12% more recorded tokens including revision cost**. Retain the frozen procedure; do not promote this candidate or tune it on these outcomes.

The reversible registry worked on the declared cases: all **36,040 later checks** passed, including **288 injected schema/digest recoveries**. These are useful engineering results, separate from a learning-performance gain.

## Why this experiment follows A5

Run91 established an exact label certificate and the cost trade-off between ordinary class-aware partial search C and additional heuristic refinement S. S reduced distance work but increased elapsed time. This creates a concrete procedure question: can experience improve how a learner compares, acquires and selects the next method? [GEPA](https://arxiv.org/abs/2507.19457) provides prior art for execution-feedback prompt evolution; this study tests one bounded revision, not a reproduction of its complete optimization framework. [A-MEM](https://arxiv.org/abs/2502.12110) motivates revisable retained experience; its reported effects do not establish this implementation's benefit. Targeted abstract/method-overview reading informed the design.

The meta learner actually inspected the shared A5 packet and frozen procedure, then submitted a 1,272-character advisory revision. It emphasized declared use horizon, setup/acquisition/verification cost, and repeated measurement when small timing differences could affect selection. It did not submit a ready-made method or change authority. Exact submission, artifact, receipt and release bindings were checked. The revision was frozen before the eight later acquisition calls; the coordinator did not write it.

## Reliability repairs and verification

Independent preflight found and closed three important host defects: non-broker execution notifications could escape a request-only check; a started folder without a terminal receipt could disappear from admission accounting; and schema-valid replacement method bytes could bypass the original acquisition binding. Additional corrections covered settled tool inventory, transitive code seals/fresh import caches, failed-phase costs, and separating deterministic evaluation from model-dispatch headroom. The real zero-inference check observed 16 disabled MCP servers; nine actual calls then used only the permitted dynamic tool. Detecting an unexpected event would not by itself prove that an unauthorized effect had been prevented.

Sixteen unit tests, independent admission/adversarial fixtures, and 1,802 source-free later checks preceded release. Final audit checks the real native submission/receipt chains, all later records against a separate exact integer formula, saved-method identity, fault/reload decisions and cost boundaries. Numerical replay is same-data reconstruction, not independent efficacy replication. Controlled fault fixtures do not prove broad hostile-host security or full agent-service recovery.

## REL and programme decision

The tested acquisition-procedure revision is retired for this use. We keep C, the sound certificate engine, bounded executable candidate interface, real acquisition receipts and reversible registry. No extra threshold sweep or rephrased comparison is justified by a clear artifact tie.

A separate small update to REL's optional host-integration guidance makes the verified interface gaps explicit: observe non-broker routes without confusing detection with prevention; keep orphan attempts unresolved before further dispatch; and recheck prior artifact bindings when activation relies on them. It is applied only after the protected study closes, with preserved base bytes and review. It is a scoped contract clarification, not a performance or universal RSI claim. The core loop stays unchanged.

A1–A6 now have concrete development evidence or an explicit negative decision in the stable programme map. They do not yet constitute a demonstrated better integrated brain-inspired architecture. The next scientific step is an integrated, independently sourced workflow where reusable methods and current information have a demonstrated joint value, using the retained ordinary components and counting acquisition/maintenance costs. Broader host/domain confirmation remains separate. These completed studies close the requested A5–A6 development pass; they do not establish universal improvement or algorithm novelty.
