# Host integration for repeated adaptation

Use this only when connecting the skill to an agent harness or claiming that a lesson persists beyond the current context. The skill is instructions, not a scheduler, memory service, or code-reloading mechanism. A host can implement the following contract with its own APIs; no particular framework or storage product is required.

1. **Load and identify.** Load the skill from a trusted location and expose the exact version or digest of the entrypoint and references used. If a protected run depends on those bytes, bind a run-local immutable snapshot or exact manifest before exposure. A later shared edit must not silently change the active run. Expose the actual operation-specific arguments, limits and execution scope of available tools, including restrictions that change between execution phases; a broad parameter list alone may omit restrictions enforced by the adapter. Keep required task outputs distinct from merely permitted or host-reserved paths in the existing task contract. Any tool projection must agree with that source; extra serialization or repetition needs its own cost evidence.
2. **Observe a material cycle.** Make the user's objective and authority limits available; capture the selected action, actual tool result or feedback, failed attempts, resource use, and a timestamp or sequence ID. Preserve permitted raw results, including rejected results, as inert evidence before validation can discard them. Use host-controlled receipt paths and validate external identities before using them in paths; failed persistence and unknown cost must remain visible. The agent's self-critique is a hypothesis, not an observed outcome. In-run adjustment may use observed feedback immediately within the existing authority boundary.
3. **Carry state only when authorized and verified.** If durable memory is available and its use is authorized for this task, check its permitted audience and persist only the minimum source-bound lesson needed, with scope, version, applicability conditions, expiry/recheck trigger, and next discriminating check. An authorized, audience-restricted project memory may retain the minimum source identifier needed to recheck that lesson; keep private source content and credentials within their authorized boundary and omit them when unnecessary. General shared skill memory should carry de-identified transferable lessons, not private task data; reuse alone does not authorize copying data between those audiences. Permit an explicit no-new-lesson outcome: preserve prior valid state and the cycle feedback without inventing a lesson to satisfy a nonempty-update requirement. Verify readback, then on the later cycle record whether a retained lesson was retrieved, applied, adapted, or rejected. If memory is unavailable, unauthorized, or write/readback fails, keep the lesson in the current context and report that cross-session retention was not established. At an imminent context boundary, leave a compact, minimized handoff only on an already-authorized surface; do not create a new memory or export destination for it. If none will persist, state that the next cycle must recheck the underlying evidence.
4. **Coordinate shared state and spend.** Where agents share writable artifacts, require exclusive ownership or a write-time version check; on a mismatch, reread and reconcile instead of overwriting. Define whether a paid-call cap covers the agent team or a wider account and identify every in-scope spender. Use one atomic admission and reservation covering those spenders before calls; alternatively use a provider-enforced hard limit or isolated budget that bounds the same scope. If atomic admission is unavailable, serialize calls through one authorized owner only when every in-scope spender must use that owner and every attempt is recorded. Otherwise stop further calls under a strict shared cap; separate local checks cannot guarantee an account-wide limit against uncoordinated spenders. A started attempt without a valid terminal receipt remains unresolved before further dispatch. This contract grants no agent access to another role's protected inputs.
5. **Keep shared changes separate.** Stage reusable skill or harness edits beside the active version; preserve old bytes and rollback. Admit them using [skill-evolution checks](skill-evolution.md) at the strength of the claim. The task-local loop may continue with a verified lesson while the shared edit awaits review. A host must supply actual permissions, isolation, restart/reload, and rollback if those operations are needed; this file does not grant them.
6. **Test the interface.** On a distinct source-free or development task, check trusted load/version, advertised tool contracts against the actual adapter with a valid call and relevant rejection, and the no-memory path. For a restricted-tool claim, include non-broker execution events in the checks and disclose observation gaps; detecting an unexpected route does not establish that its effect was prevented. Where durable memory is available and authorized, also check successful write/readback, a no-new-lesson update that preserves earlier knowledge, and stale or contradictory lesson rejection. Where shared edits are supported, test rollback after a bad candidate. Where shared writing is supported, test a stale write. For paid calls, verify the selected control's scope and enforcement: challenge simultaneous reservations for one remaining slot if using an atomic ledger, or check the provider hard limit, isolated budget, or exclusive custodian path actually covers every in-scope spender. Exercise a saved artifact through its advertised invocation after a fresh start, and preserve its declared read dependencies in both execution and validation environments. A working directory or a mocked tool call alone does not qualify those paths. Measure whether the host's hooks add unacceptable delay or cost. A passing interface test establishes those hooks for that host version, not better performance on later user tasks.

When an agent must act without another role's answers or protected state, expose an explicit projection of permitted fields in task packets, manifests, logs and diagnostics. Answer-derived hashes can supply an equality check even without answer text; private artifact paths can reveal an unintended route. Keep those fields with their owning role unless sharing is authorized. Check the actual agent-visible files and tool responses, including nested metadata, rather than relying on an empty history setting. Verify that needed public facts and provenance remain available and that a forbidden-field fixture is rejected. This applies to role-separated work, not ordinary workflows where that information is intentionally shared.

When a completed model phase is followed by potentially long or fallible verification, persist its identity, recorded usage pointers and frozen-output binding before that verification starts. Keep model completion, verification and whole-task completion distinct, and budget verification explicitly. Recovery may reconcile saved evidence; it must not invent a final receipt or silently convert post-budget checking into an in-budget success. When later activation relies on that verified artifact, match its bytes to the recorded binding; schema validity alone does not establish identity.

When a frozen or archived state becomes an **editable working copy**, byte equality alone does not establish readiness. After the transfer, exercise the intended authorized operation through the actual adapter and check a relevant protected-path rejection. Inherited read-only modes or permissions can contradict the advertised contract. Correct only the new working copy within its granted authority; keep the original snapshot and protected inputs unchanged. Recheck when that transfer path changes, not on every ordinary action.

## Optional execution backends

When an external sandbox or worker is needed, distinguish requested controls, documented support and enforcement observed on the actual host. Record only relevant prerequisites and capabilities, the enforcement owner and version, input/output boundaries, explicit command deadline, resource limits, effective network policy and cleanup evidence. Missing required isolation must not silently fall back to an unrestricted execution path. A contained code worker does not cover tools the surrounding agent invokes elsewhere.

Treat request acceptance, readiness, command exit and resource removal as different states. Keep the original operation identity after a timeout or disconnected stream; reconcile it before repeating a possible effect. A retry key has only the lifetime and restart guarantees the backend actually supplies. Pause, snapshot and shutdown may preserve different state. When a restored worker retains saved policy, recheck its effective permissions against current task requirements; current defaults may not replace saved policy. Verify necessary artifact readback and documented crash durability before describing acknowledged guest writes as durable task completion. Test the required successful path and a relevant rejection or interrupted path at integration time; repeat when the adapter or its assumptions change, not on every ordinary task.

When an adapter crosses operating-system or process boundaries, verify each side's actual interpreter, workspace path and service endpoint. A reachable client does not establish that its execution mount or local model transport reaches the intended destination. Make any translation explicit, inspect the effective execution boundary, and test saved-state use and recovery through that route. Qualify model transport separately from code execution; preserve the existing working route and do not silently fall back to unrestricted execution. This applies when those boundaries change, not as an extra preflight for every task.
