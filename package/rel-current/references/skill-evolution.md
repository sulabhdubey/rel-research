# Evolving a reusable skill

Use this for a shared instruction, prompt, skill, memory policy, or harness workflow. Keep task-local adaptation fast; change the shared improvement procedure more slowly and only on relevant evidence. The component being changed is the treatment, including when that component is the harness. Do not edit instructions bound to an active protected evaluation; preserve its exact version or rebase the evaluation explicitly.

1. **Diagnose before editing.** Inspect the user's outcome, current version, last verified lesson, exact failure and successful controls, and relevant current primary sources or documentation. Locate the cause: task execution, missing knowledge, unavailable tool, weak feedback, evaluator error, stale source, environment, or reusable instruction. A wording change cannot repair an absent capability. Record when a new rule would apply, when it would be harmful, and the next observation that would decide whether to retain it. If two material cycles produce no direct evidence toward the primary outcome, revisit the whole path even if local decisions changed; a closed prerequisite can justify only bounded continuation.
2. **Name the claim and make one bounded candidate.** Distinguish a factual or internal-consistency correction, a working procedure, an observed learning pathway, better later task outcomes, and broader transfer. Each needs different evidence. Preserve old bytes, source rationale, rejected alternatives, and rollback path; pin the candidate version and change as few components as attribution allows. Keep entrypoints focused and conditional detail in references; fewer prompt bytes alone do not establish lower complete task cost. Do not place private task data or benchmark answers in a general skill. Use the compact [change record](../assets/skill-change-record.md) when no stronger ledger exists. If the host supports durable state, bind a lesson to its source, scope, version, and recheck trigger; do not assume state was saved or loaded without a receipt.
3. **Preflight proportionately.** Validate format and links. For a purely nonbehavioral citation, metadata, or link correction, verify its source, dependencies, and affected paths without requiring a separate task trial. For a behavior-changing candidate, exercise a distinct realistic **in-scope** task and an existing working path; test another domain only for a broad portability claim. For a procedural or harness change, check the actual behavior. Challenge ambiguity, no-tools operation, missing memory, conflicting feedback, untrusted instructions, and an ordinary low-risk task that should proceed directly when relevant. Static checks and self-authored examples establish consistency and interpretation, not a general performance gain.
4. **Compare only at the strength claimed.** For a comparative later-task or productivity claim, freeze old and candidate versions, fresh tasks, initial task context and context budget, rubric, order rule, permissions, budget, and every **noncandidate** model/host/harness component before outputs. The candidate harness itself may differ, including the later context its memory loader retrieves. Use independent old/new sessions and a verifier blind to version where feasible; preserve failed and malformed attempts. Include changing-state cases for long-running skills and test whether a lesson was written, retrieved, applied correctly, and revised or rejected when stale. To attribute a later gain to retained experience, use a matched no-retained-state control or another adequate isolation design; without one, report observed reuse and outcome with attribution unresolved. Even a matched control does not remove every possible confound. Keep exploratory or exposed tasks separate from fresh confirmation.
5. **Measure multiple outcomes and costs.** Report separately: procedure loaded and executed; knowledge/method acquired and later applied or rejected appropriately; task success and quality; time to diagnose, repeated errors, false stops or unsafe proceeds, and later-cycle transfer; software/harness reliability; critical authority, privacy, security, and evidence errors; inclusive tokens, wall time, compute, money, and human work when measurable. Label unavailable measures as unknown. Compare paired tasks and inspect worst-case regressions, not only average score. A safety regression blocks promotion despite higher average task success. A ceiling tie or small pilot leaves improvement unresolved. When diagnosing token overhead, distinguish initial input, model request count, later context growth, output, and cached input in the recorded attempts. Tool-action counts or source-read bytes alone do not explain total tokens. An arithmetic decomposition is descriptive unless an intervention identifies the cause. Check whether expensive work serves a required deliverable, necessary verification, or an optional artifact; write permission alone is not a completion requirement. Inspect actual tool replies before diagnosing lost output, and preserve useful repairs that follow an early passing check. Check the complete trajectory after compression or output reduction, including retries and extra summary calls; a smaller prompt or cheaper phase can still increase total cost.
6. **Promote, revise, or roll back.** Admit a verified correction or retain a candidate only for the scope its checks support and when its benefit justifies cost and no unacceptable regression appears. A justified no-change decision is useful; do not force a rewrite each cycle. Before replacing shared bytes, compare them with the candidate's recorded base; on drift, reconcile and recheck rather than overwrite another change. Do not tune on exposed confirmation tasks and call them fresh. Keep provenance and dependency links so a withdrawn source triggers recheck. Monitor later work for drift, stale assumptions, and skill–host interface changes; use a new version and fresh evidence for subsequent claims. Where a protected run depends on shared files, bind an immutable run-local snapshot or exact hashes before it starts; a later shared edit must not silently change that run. Reapply this process to the improvement procedure after material use, not on a timer or for its own sake.

This is a portable decision protocol, not a runner. It helps only when a trusted host loads it, feedback is observable, and permitted state survives long enough to affect later action. It cannot promise improvement for every model or change model weights.
