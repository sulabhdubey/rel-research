# Select useful skills and maintain them from evidence

Use this when choosing among available skills, composing a task workflow, or an observed result calls an existing skill into question. Selection is a decision under the current task's constraints, not a guarantee of the globally best skill.

## Choose for the next action

1. Identify the immediate outcome, artifact type, available host/tools and authority. Honor skills explicitly requested by the user. Start from the host's supplied catalogue or a targeted discovery mechanism; do not crawl unrelated private projects to build an inventory.
2. Match descriptions to the actual operation, then read the selected entrypoints. A keyword match or a high rating is not evidence that a skill fits. Resolve a stale selected path through the supplied catalogue or targeted discovery. If a required skill remains unavailable, explain the limit and continue only work that does not depend on it; do not silently substitute another method for a specifically required skill. Check prerequisites and the actual tool interface before depending on a capability. Do not pretend unavailable instructions or tools ran.
3. Use the smallest complementary set that covers a concrete gap. Let this loop coordinate evidence and adaptation while domain skills supply specialized methods. Keep one clear owner for each action and avoid duplicate checks or conflicting procedures. A simple task may need no additional skill.
4. Resolve conflicts using the user's goal, applicable instruction authority, actual interfaces and verified requirements. A skill cannot authorize spending, disclosure, destructive changes or another skill's tools. Do not import a task-specific exception as a universal rule. If a conflict prevents a required action and cannot be resolved, explain the exact sources and ask only for the missing decision.
5. Reconsider selection when the operation, environment or evidence changes. Reuse the relevant skill already read when it still applies; repeated loading and a full inventory on every command add cost without establishing better selection.

## Evaluate a skill that was actually used

Bind observations to the skill version, task and host. Record what decision it changed, the outcome, mistakes or regressions, and material overhead. Reading a skill or passing a formatting check does not establish usefulness. A failed task alone does not establish a bad skill: first distinguish missing/incorrect guidance, failure to follow valid guidance, bad feedback or source evidence, unavailable tools, and host enforcement problems.

Recommend one of these scoped dispositions:

- **Keep:** it supports a relevant workflow or a useful invariant; state the tested scope.
- **Repair or clarify:** a source or interface check reproduces a defect; specify the minimal correction and affected behavior.
- **Compare:** benefit or overhead is uncertain; name the decision-changing comparison rather than asserting improvement.
- **Combine or narrow:** overlapping skills cause duplicated work or conflicting triggers; inspect callers and compare retained behavior before restructuring.
- **Defer:** it is not relevant to this task, or evidence is insufficient. Low usage is not proof of low value.
- **Retire for a stated scope:** the approach repeatedly harms the outcome or is superseded by a checked alternative. Preserve history and a re-entry condition; distinguish this recommendation from uninstalling it.

Include only recommendations material to the user's work. Do not automatically delete, disable, uninstall or rewrite other skills. Make permitted edits through their versioned change process, checking distinct realistic use and the previous working path. For a global collection audit, get a task that actually authorizes that scope. Keep private task details out of general shared instructions.

This reference adds selection and review guidance. It does not implement a catalogue service, enforce routing, or demonstrate that the selected skills improve every model.
