# Real-project failure qualification

20 October 2026. Private, sanitized evidence update.

**No unresolved repair qualified in this bounded three-project screen.** The
planned ordinary-versus-REL comparison did not run. The result does not imply
that these projects have no defects, and it does not establish better decisions
from REL.

## Why this screen was different

The preceding [interrupted-transfer qualification](EVIDENCE_2026-10-20_INTERRUPTED_TRANSFER.md)
ended with four ordinary workers solving all scored cases. This run therefore
inspected current real-project failures before dispatching another worker.
The plan required a reproduced, contract-supported defect, a relevant past lesson,
authorized isolated repair, and remaining ordinary-worker errors before a later
comparison. Up to two ordinary screens and six conditional comparison attempts
were planned; none was dispatched.

No current product defect was established; do not weaken the gate. |
| B: recent graph/handoff work | Completed project turns report passing hosted and focused checks. A local passing receipt was found to be months old and excluded from current-health evidence. | No unresolved repair found in the inspected scope. Reported hosted tests were not independently rerun. |
| C: broader launch remains blocked | Current reports record scoped implementation and delivery checks as passing, while external acceptance and release qualification remain open. | A launch blocker is not automatically a repairable implementation defect. |

## What actually executed

A small read-only Node diagnostic recomputed identity and digest links, verified
an Ed25519 signature with a public key, and rehashed selected source files. Eight
identity/binding booleans and five overlapping control booleans passed. These are
not thirteen independent experiments. Selected bytes did not change during the
read. In-memory changes to signed data and ledger content were detected.

The diagnostic imports no project code and reads no private key. It does not
render current output, rerun the project suite, discover all new dependencies,
regenerate signatures or demonstrate semantic product correctness. Public-key
verification establishes only the checked identity and signature relationships.

The stale local receipt is a correction to the investigation, not a project bug.
Neither an old pass nor a current chat claim was treated as complete qualification.

## Cost and claim limits

Study-worker calls, worker tokens, feedback turns and GPU inference were zero.
This was **not zero-cost research**: coordinator model use, tool operations,
source inspection and package work occurred. Complete coordinator tokens,
engineering time, money and physical/remote energy are unknown. The diagnostic
measured approximately 0.067 seconds internally, excluding process startup.
Package validation is recorded separately in private evidence.

There were no model-control arms, repair scores, tokens-per-success estimate,
efficiency gain or causal learning claim. Signature/tamper checks are software
controls. The three project leads are purposively selected, not a population
sample. Local source pointers and receipts are retained privately; this sanitized
summary is not a fully reproducible public project benchmark.


Package maintenance also exposed a Windows newline-conversion defect in this
run's documentation writer. The original failed bytes and whitespace-check result
were retained. The writer now explicitly preserves LF, checksums were rebuilt and
the scoped package checks rerun. This repairs the study's delivery tooling; it is
not an independently selected project failure or evidence of better model repair.

## Consequence for REL

The core instructions and helpers remain unchanged. Existing instructions already
require checking a rejection's cause, source freshness, ordinary capability and
proportionate cost. This run records application of those checks; it does not
establish their superiority over ordinary competent work.

The open question remains whether past experience improves a later repair beyond
equally informed ordinary work. Reopen with a concrete current failed receipt
after ordinary repair, a reproducible isolated source snapshot and a relevant
lesson. Do not reuse a resolved issue, a legitimate stale-source rejection or
missing external acceptance as a fabricated model failure.
