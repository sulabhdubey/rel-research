## Actual work and comparisons

Thirty-four fresh native Codex model sessions used gpt-6-luna/medium with scoped
tools, existing offline Docker execution, 60 actions and 900 seconds per attempt.
There were 26 graph sessions, one learner-authored procedure-development session,
six accounting-transfer sessions and one post-comparison repair. No extra paid
API was used. Generated operational cases are not independent production data.

Two origin learners used an equally available pinned NetworkX library to build
executable matching and minimum-cost-flow methods. Later work varied objectives,
negative weights, required/banned elements, balance conventions, lower bounds
and infeasibility. Graphs had 48–120 vertices. Eighty small oracle checks were
separately enumerated; larger reference cases used the same public library.
All future graph semantics were already in the origin contract. Later sessions
branched from two complete origin bundles, rather than accumulating each other’s
discoveries. This is not a long compounding learning sequence.

ordinary work. It failed its adoption criterion and was not installed. Actual
library invocation and working methods were observed; a filename or saved
method description was not counted as execution. No accuracy advantage appeared.

A context-copy defect in the evaluator omitted permitted historical imports.

lost the distinction between required and optional edges. It failed 9/12
diagnostic cases despite passing its original tests. All 24 later artifacts
passed that diagnostic. This is not an untouched confirmation endpoint.

## Learner-authored procedure and subsequent repair

The origin learner’s next session repaired the matching bug and proposed a
scoped verification method: derive aggregates from the final returned items,
with an explicit exception when the aggregate is not derivable from those items.
This is an existing verification technique, not a novel mathematical algorithm.

Two new accounting profiles reconciled unordered and duplicated usage records,
conflicting identities, malformed vectors, missing completion references and
thread-versus-turn cumulative accounting. Each profile had 12 cases with 24–48
attempts per case. A latent-ledger generator and separately implemented reader
agreed before the model sessions. All arms received the same prior evidence;
only the evolved arm activated the learner’s exact proposal as an instruction.

| Policy | Correct tasks | Correct cases | Inclusive reported tokens | Tokens per task success |
| --- | ---: | ---: | ---: | ---: |

The proposal was visibly used in code and checks. It met the small exploratory
quality screen against the frozen arm, while ordinary work tied its accuracy
and used fewer tokens. Two profiles cannot establish a stable treatment effect.
The frozen arm’s failure was an undeclared-turn `KeyError`, not an aggregate
recomputation error; the hypothesized causal mechanism is therefore unresolved.
The proposal remains a scoped candidate rather than a mandatory generic rule.

The failed artifact was subsequently repaired by a fresh learner session using
the updated generic core. It passed all 12 original regression cases and 24
fresh cases across both accounting modes. Its old comparison score remains a
failure. A preparation attempt exceeded the bounded result envelope; separate
validation batches corrected transport without increasing the capture limit.
No learner was dispatched in that failed preparation.

## Engineering changes

- The future research host retains rejected raw guest results before strict
  validation, reports receipt-storage errors and exposes remaining action/time
  budget. Interrupted scored artifacts remain available without being counted
  as completed submissions. The historical host and results remain unchanged.
- Source-bound accounting distinguishes accepted, rejected and missing receipts,
  prevents duplicate container identities from being charged twice, and keeps
  incomplete costs unknown. All 114 tool-guest receipts in the graph sessions
  were found, with no missing or surplus receipt.
- The optional scoped Python host adds operation-specific tools, journaled
  writes, workspace/authority binding, source restoration, restart checks and
  offline execution. Malformed responses/calls and missing or invalid token
  counts now preserve honest terminal/accounting outcomes. Output truncation
  is visible in tool feedback. Valid tool batches are allowed; a failed call
  stops later effects in that batch.
- The generic core clarifies actual lesson application and changed-behavior
  checks. The host reference clarifies rejected-result preservation and saved
  artifact invocation with its declared read dependencies. These are verified
  clarifications, not demonstrated performance gains from those exact words.

## Portability results and limits

The exact delivered host passed real offline normal execution, code corruption,
known-revision restoration, restart/readback, output-truncation and bounded-hang
checks. The tested containers were removed and absence verified. Ordinary
package tests also run on a Linux Python 3.12 guest; this does not qualify a
Linux Docker controller or a model server running inside that guest.

Seven local-model attempts used already-cached Llama 3.2 3B or Qwen 2.5 7B
Instruct with CPU inference only. Earlier attempts timed out, produced prose,
repeated invalid calls or generated invalid Python. One proposed one-call-only
policy unnecessarily rejected a valid batch and was retired. An actual isolated
Python import-path defect was also repaired. These changing exploratory
configurations are not a matched local-model comparison.

A fixed saved-method runner then let Llama execute the existing learned method
through a real tool call, receive its result and finish the workflow. All 12
outputs passed independent checks. The method was supplied, the invocation was
specified and the helper was investigator-built: this does not demonstrate
independent local-model capability acquisition or broad semantic reliability.
The live call used host SHA-256
`2b9c2009df82f8f23136104f68add4cbffedbefe9e107fc633b10f52fa2fd1da`.
The delivered host adds four output-capture fields; that additive correction
received fresh actual-guest and offline tests, without repeating model inference.

## Cost and unresolved claims

Across all 34 native sessions, exact reported usage was 8,785,468 tokens,
including 7,425,792 cached input tokens; uncached input plus output was 1,359,676.
There were 625 tool actions and 5,250.52 summed dispatch seconds. The 163.79
seconds for corrected regrading are separate. Concurrent durations are not
campaign elapsed time. The 33/34 complete-task count is descriptive across
different phases, not an independent reliability estimate or a repaired score.

Local attempts are accounted separately; timed-out server work remains partly
unknown. Parent research, review and complete preparation costs, currency and
physical/remote inference energy are not fully measured. Tokens are not money
or joules. No extra inference requests were made merely to change an unfavourable
comparison into a win.

Semantic memory reliability, consistent autonomous acquisition, sustained
procedure improvement, wider independent host/domain results and superiority
over equally informed ordinary work remain open. Instruction coverage, working
software, observed reuse and comparative benefit are different evidence levels.
No universal RSI, exponential improvement or perfection claim is supported.
